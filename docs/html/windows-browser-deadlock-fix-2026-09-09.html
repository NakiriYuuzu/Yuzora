Windows Browser 死鎖修正

2026-09-09 · 工作區版本 0.0.9-beta.3 · 分支 release/v0.0.9-beta.3

已修正與使用者症狀高度吻合的原生 webview 建立方式。本機編譯、既有相關測試與 Clippy baseline 通過；尚未在 Windows 重現原始問題或驗證修正後的安裝包。使用者實際安裝版本與觸發網址尚未確認。

問題與證據

使用者回報 Windows 開啟 Browser 後，各功能無法顯示內容；點擊檔案仍有反應，但應用也無法關閉。原始 preview_open_url 是同步 Tauri command，直接呼叫 Window::add_child。

本機 Cargo.lock 的 Tauri 版本為 2.11.5，其 WebviewBuilder 原始碼文件明確記載：

On Windows, this function deadlocks when used in a synchronous command or event handlers. You should use async commands and separate threads when creating webviews.

來源：本機已解析套件 tauri-2.11.5/src/webview/mod.rs，第 287–290 行；同版本 API 文件；套件引用的 WebView2 issue #583。遠端連結供追查，本次直接核對的是本機套件原始碼。

死鎖會阻止原生事件與 IPC 推進，與內容載入及關窗同時停止的描述吻合；本次沒有 Windows 執行期堆疊，故不能斷言已排除所有其他原因。

變更

程式變更限於 src-tauri/src/preview_webview.rs：

  • 將開啟、bounds、visibility、close、reload 五個 command 設為 #[tauri::command(async)]。Tauri 負責將原生操作送到主執行緒，呼叫端不再佔住主執行緒等待結果或生命週期鎖。
  • 歷史查詢／導覽的 with_webview 主執行緒回呼改用 try_lock。如果建立／關閉正在持有共享鎖，回呼回傳錯誤，避免主執行緒等待正在等它完成工作的 command。既有輪詢會稍後再讀取；競爭中的手動歷史導覽可能回報失敗，由使用者重試。
  • 沿用既有 nativePreviewQueue，維持前端開啟、導覽、顯示與關閉操作的先後順序及 session ownership 檢查。

Windows 尚待驗收

  1. 以包含本次變更的 Windows build，開啟 Browser 並載入回報時的網址；另測一般 HTTPS 與已啟動的本機 HTTP 服務。
  2. 開啟檔案，確認編輯器實際顯示內容；切換其他功能，確認 Browser 原生圖層正確隱藏或關閉。
  3. 快速切換網址、返回／前進、重新整理、調整面板大小，並在載入期間關閉 Browser 分頁。
  4. 用視窗關閉按鈕及 Alt+F4 確認應用能正常退出。記錄 Windows／WebView2 版本、候選 build 與結果。
