架構評估 · 2026-09-09 · 工作分支 release/v0.0.9-beta.3 · 尚未批准遷移

GPUI 適合作為下一代工作面；
目前應先驗證，再決定全面遷移。

建議：有條件採用 GPUI Kit 作為原生桌面方向，先做獨立的 HERDR Terminal＋Browser 技術原型。現階段不建議全面重寫。

如果目的只是只發布 Windows 與 macOS，保留 Tauri 即可：目前 release matrix 已經只有這兩個桌面平台。若目的在於長期採用 Rust、改善高頻互動的可控性、統一桌面渲染，GPUI 才有足夠的評估價值。

本評估以保留目前 HERDR、Editor、Git、Database、SSH/SFTP、Browser 功能為假設；「只提供 Windows／macOS」解讀為桌面客戶端範圍，保留 Windows 所需的 WSL2 與遠端 Linux host。沒有假定要增加 LSP、重建 PTY，或刪除 Browser。

1. 最新上游狀態

使用者提到的「GPUI（Shadcn）」，最接近的是 Longbridge 的 GPUI Kit。原 gpui-component 專案已改名；v0.6.0 於 2026-09-03 發布，gpui-component 仍是其中的 styled UI layer，官方建議新應用依賴 gpui-kit facade。

它與 shadcn 的關係是設計及分層理念，不具 React／Radix／Tailwind 原始碼相容性。主工作面的元件、Zustand 狀態協調、事件與動畫都要移植。GPUI 自行繪製 UI，不能將「原生 Rust 應用」理解為每個控制項都是系統 AppKit／WinUI widget。

  • Kit 已提供 Dock、可拖曳分頁、虛擬列表、DataTable、Command palette、Editor 與 Markdown／HTML rich text；常見工作面元件有可用基礎。
  • v0.6.0 對 Input、Editor、Dock、Table、WebView 等 API 有多項 breaking changes，並採用 gpui-pre 0.3.x 家族。GPUI 官方仍說明 pre-1.0 與版本間的 breaking changes。原型應固定相容版本與 lockfile。
  • Kit v0.6 安裝文件列 macOS 15+、Windows 10+、Rust 1.90+。這是文件列出的開發／安裝要求，不能直接當作所有最終產物的最低執行版本保證；舊版 macOS、Intel Mac、Windows GPU／DPI 環境需要另行驗證。
  • Kit 已加入可存取性語意；上游 GPUI 有 AccessKit 支援。這不等於 Yuzora 的終端、編輯器和自訂 UI 已通過 VoiceOver／Narrator 驗收。

官方宣傳的 120 FPS、20 萬行編輯能力屬於上游說明，沒有在本次當作 Yuzora 的效能測試結果。

2. Yuzora 現況使哪些部分容易，哪些部分困難

範圍遷移方式與主要成本判斷
HERDR／host helperyuzora-host 已是沒有 Tauri dependency 的 Rust crate；桌面 HERDR service 多為 adapter。保留 runtime、protocol、ownership 與 helper，另接 GPUI 事件。最有利的重用基礎。
SSH／SFTP／DB／GitRust 核心邏輯可沿用；desktop service 仍有 AppHandle、Emitter、State 與 Tauri async runtime 依賴，需拆開事件、路徑與生命週期 adapter。可重用，但不是直接複製即完成。
側欄／分頁／表單／資料表採 Kit 元件重建互動。設計 token、文案與需求可保留，React／Radix 元件不能直接使用。元件選擇合適；中至高工作量。
HERDR Terminalxterm、FitAddon、IME、選取、鍵盤、輸出佇列及 transport 配合需重寫。Kit v0.6 catalog／source tree 中未找到可直接替代 xterm 的 Terminal 元件。原生化的首要風險。
Editor／Diff／MarkdownKit Editor 可支撐語法編輯；需移植 document revision、dirty buffer、檔案衝突、CodeMirror merge 與 undo 語意。Kit 的 Markdown 顯示不等於 Tiptap 視覺編輯。高工作量；目前不需 LSP 是有利條件。
Browser可使用 gpui-wry 保留系統 WebView；網址／tunnel 邏輯可沿用，視窗、bounds、focus、overlay 與關閉流程需重接。可行但 integration 仍屬實驗性。
安裝／更新／桌面整合替換 Tauri bundler、updater、process、dialog、clipboard、opener、window-state 整合。需處理原使用者設定、keyring identity、更新渠道與安裝升級。獨立工作流，GPUI 不會自動完成。

依目前 Git 追蹤檔案計算：src/ 正式 TS／TSX／CSS 為 233 檔、49,458 行；前端測試為 172 檔、50,161 行。Rust host 為 45 檔、37,407 行；desktop 為 43 檔、27,625 行，Rust 統計包含 inline tests。統計排除 vendor、建置產物與未追蹤文件；它衡量規模，不能換算成精確工期或重用百分比。

既有 Vitest／jsdom 測試可作為行為規格參考；依賴 React、DOM、CodeMirror 的測試不能直接執行在 GPUI UI 上。

3. 兩項必須先解決的整合問題

Terminal 必須繼續遵守 HERDR 的終端語意。目前 xterm 設定 scrollback: 0，接收 HERDR frame，處理 full／增量序列，捲動由 runtime 控制。GPUI 端不能只是開一個新的 local PTY，也不能把遠端捲動任意改成本機 scrollback。

原生方案可評估 alacritty_terminal 等終端狀態引擎，再實作 GPUI renderer 與 HERDR connector adapter；引擎本身不是可直接放進 Dock 的 GPUI UI。需要驗證全畫面 TUI、ANSI／Unicode、中文組字、寬字元、選取、滑鼠、快捷鍵、貼上、resize、controller／observer、first-full／resync 與重連時不重送輸入。

GPUI 與 Kit 採 Apache-2.0；Zed 的 terminal_view 則標示 GPL-3.0-or-later 且依賴 Zed editor／workspace 等模組。不能因 GPUI 是 Apache 授權，就假設 Zed 整套 Terminal 可作為同授權的獨立元件直接搬用。

保留內建 Browser，就仍需網頁引擎。gpui-wry 的 README明確標示 experimental、目前支援 macOS／Windows，且 WebView 會覆蓋其 bounds 內的 GPUI 元件，建議獨立視窗或 Popup layer。

Yuzora 現在的 Tauri child WebView 本來也有這個覆蓋問題，已透過 overlay gate 在開啟 modal／popover 時隱藏。改用 GPUI 不會自動消除此限制，必須重建並驗證遮蔽、焦點和生命週期。若只想完全移除 Tauri app framework，保留 Wry 可成立；若要求完全沒有 WebView，則現有內建 Browser 需求必須改為外部瀏覽器或另選網頁引擎。

短期以 WebView 保留 xterm／CodeMirror 可以降低初次移植量，但會保留 JS、WebView 資源與混合焦點成本；不應將此方案的成果當作「完整原生化」的效能證據。

4. 只發布 Windows／macOS 的真正影響

現有 release.yml 的 matrix 已是 macOS Universal（arm64＋x86_64）與 Windows x64；Linux 用於部分 CI、資料庫整合與 host runtime。更換 UI framework 不是縮減桌面發布平台的必要條件。

Windows 目前透過 WSL2 使用 Unix HERDR runtime。GPUI 只更換桌面呈現層，WSL2、遠端 Linux helper、SSH routing 與 host identity 仍需保留；不發布 Linux 桌面，不代表可以刪除 Linux runtime 建置與驗證。

移除 Tauri 後，還是需要兩平台建置、macOS .app／DMG、codesign／notarization、Windows installer／簽署，以及 updater 的下載驗證、套用、失敗恢復與舊版升級路徑。這些可以使用獨立工具完成，但不由 GPUI renderer 代辦。

5. 建議的技術原型與採用門檻

先以 1–2 週作為驗證 timebox，不是功能完成承諾；驗證未通過即可終止，避免把全案遷移當作已決定事項。後續實作需另獲授權。

  1. 接真實 HERDR：建立小型 GPUI Kit 工作面，只接既有 session／terminal adapter；兩平台各運行一組多分割 TUI，驗證 IME、選取、貼上、resize、remote scroll 與斷線重連。
  2. 接 Browser 與一個 Editor：驗證 Browser 在 panel resize、tab 切換、modal、popover、Command palette 下的遮蔽和焦點；編輯器驗證 dirty buffer、存檔、外部衝突與 Unicode。
  3. 同條件測量：比較 release build 的冷啟動、可互動時間、輸入延遲分布、frame time、閒置 CPU、GPU／耗電及總記憶體；記憶體納入 WebView／helper，固定 terminal 數、輸出負載與 Browser 狀態。
  4. 打包一輪：確認 macOS arm64／Intel 與 Windows x64 的目標環境能執行，列出最低 OS／GPU 要求，驗證設定資料可讀取與 HERDR 退出語意。

通過條件：核心操作無阻斷性退步；終端與 Browser 問題有可維護的解法；實測收益足以支持重寫成本；最低平台支援符合使用者範圍。若優勢僅是畫面風格，保留目前 Tauri 並改進 UI 的成本通常更低。

本次沒有編譯 GPUI 原型或執行 GUI／效能測試，因此無法宣稱 GPUI 版本已更快、更省記憶體或具有功能等價性。若要完整保留目前功能，應視為數月級的工程項目，精確工期需在終端／Browser 原型與功能盤點後估算。

6. 若通過驗證，建議的遷移順序

Yuzora Desktop（GPUI Kit）
  ├─ 工作面：Spaces／Agents／Dock／Editor／Database UI
  ├─ HERDR terminal renderer＋connector adapter
  ├─ Browser：gpui-wry
  └─ UI 無關的 Rust service 邊界
       ├─ HERDR／host identity／session／事件
       ├─ Files／Git／SSH／SFTP／DB／vault
       └─ yuzora-host → 本機 macOS／WSL2／SSH Linux・macOS

桌面發布：Windows x64＋macOS arm64／Intel
安裝與更新：獨立維護的打包、簽署、升級流程

先抽離 desktop service 的 Tauri adapter，保留原應用作為行為基準；接著完成 GPUI 工作面與 terminal，再遷移 Editor／Git／Database／SFTP，最後完成資料、設定、keyring、安裝與更新遷移。新 UI 不繞過既有 host／workspace 信任、owner／generation、typed protocol 與不重送寫入規則。Tokio runtime 應有明確 ownership，不在 GPUI UI thread 執行阻塞工作。

這個方向和現有 ADR 的 HERDR ownership 可以一致；若未來選擇外部 Browser、Windows 原生 PTY 或移除 Linux host，則是另一項產品／架構變更，需重新決策。
