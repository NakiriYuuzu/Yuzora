macOS 子行程 pipe 繼承強化：HERDR 等待卡住與 Companion 存活

日期：2026-10-22（Asia/Taipei）。分支：fix/macos-pipe-hardening，基底 66202bd8（PR #144 的 head），尚未 commit。範圍：PR #144 修 CI flake 時發現、列為後續工作的兩項正式程式風險。

要解決的問題

項目症狀結果
P2：HERDR 等待卡住HERDR connector release、HERDR CLI 呼叫（wait_bounded_child）、native client release 與 app 結束時的 release_all_connectors 以沒有時限的 join 等 stdout reader；若 pipe 的 write end 被別的長壽子行程繼承，reader 永遠等不到 EOF，桌面跟著卡住。macOS 已實測關閉（Linux 尚未執行，要等 PR 的 CI；Windows 僅編譯檢查）
P3：Companion 存活gateway 與 tsnet sidecar 只靠 stdin EOF 得知桌面結束；若別的行程繼承了 stdin write end，桌面崩潰後它們繼續服務。macOS 已實測關閉：gateway 的真行程孤兒測試在 init 之後、serve 期間成為孤兒；sidecar 的真行程孤兒測試執行真正的 main()，但在 init 之前（handshake 階段）就結束，serve 中的收尾（stopServing、closeWithin）只由注入檢查加假 tailnet 的 run() 測試驗證。兩邊都讓 stdin 保持開啟（Linux 規則以單元測試與模擬建置驗證，實際執行要等 PR 的 CI；Windows 仍靠 EOF）

根因

Rust std 在 macOS 上不使用 pipe2（macOS 27 之前沒有這個 API；std 的 cfg 不含 Apple 平台，目前用的工具鏈也一樣）：Stdio::piped() 先 pipe()，再分兩次設定 close-on-exec；而進行中的 posix_spawn 在 exec 完成前持有父行程所有 fd 的複本。另一個執行緒剛好在這個空窗 spawn，子行程就會在整個生命期間留著別人的 pipe 端。帶 pre_exec 的 spawn 走 fork 路徑，std 自己的 exec 狀態 pipe 也有同樣問題，甚至能讓 spawn() 本身卡住；portable-pty 的 openpty 同樣分兩步設定。Linux 的 std 用 pipe2、Windows 的 std 有 CREATE_PROCESS_LOCK，所以 std pipe 的部分只在 macOS 出現；portable-pty 的 openpty 則是所有 Unix 都有這個空窗，所以 spawn 鎖對所有平台生效。

殘餘與範圍外

  • 在 spawn 以外建立的 fd（socket、accept、socketpair 等）仍可能被任何 spawn 帶走。
  • release 的有限等待只是放手：等不到 EOF 的 reader thread 會被 detach，連同它持有的 pipe 讀端留到占住 pipe 的行程結束為止（之後不再送出事件）；connector 的 stderr thread 本來就是 detached。每發生一次這種 release，就多留下一個 thread 與一個 fd。
  • 第三方 spawn 不經過鎖：tauri opener 的 open、updater 的 touch、tauri restart；Linux 上 dialog／notification 的 helper。
  • 單一卡在 exec 的 spawn 最多讓其他 spawn 延遲 10 秒，被擋住的取鎖會占住一個 tokio worker thread 最多 10 秒；NetManager::start 在 spawn 期間持有 inner（既有）。
  • Linux：父行程在記下基準之前就死時，不論有沒有 subreaper 都退回靠 stdin EOF（Linux 的規則不把一開始就是 pid 1 視為父行程消失，因為 pid namespace 裡活著的桌面也可能是 pid 1）；Windows 沒有父行程檢查。
  • 父行程消失時，gateway 與 sidecar 的 unserve 先後只靠時間差（sidecar 每 250 ms、gateway 每 1 秒再加 0.5 秒），沒有握手；sidecar 在 ts.Start() 期間的取消要等 Start 返回才看得到，gateway 的 init 階段不看父行程，只受 5 秒 init 期限約束。
  • 契約 D5 明列不處理：env_path.rs 啟動時的 read_to_end；孫行程占住 stdout 時 git_process 把成功變成逾時；DB worker／SQLite lane／host helper 的父行程存活。
  • 同類既有、未改（lane J 發現）：server.rs 的 command_json（15 秒）與 host_bootstrap 的 execute_with_output_limit（60 秒）都讀到 EOF，別的行程占住 pipe 時，成功會變成逾時、已讀的資料被丟棄；host_sqlite 的第一個 frame（30 秒）讀到換行就結束，成功不受影響，只有 worker 沒回覆就結束時，失敗會從立即回報延後到 30 秒。三者都有上限，不會卡死。
  • 既有行為（不在這次 diff 內）：Unix 的 kill_tree（host/src/process_kill.rs）對 process group 送 SIGTERM 後，若 leader 在 TERM_GRACE（300 ms）內結束，只等待 group、不檢查結果就回傳 Ok，不會再對 group 送 SIGKILL。因此忽略 SIGTERM 的同組成員在單一 terminal_release 之後仍會存活；release_all_connectors 期限到時會對 group 送 SIGKILL，app 結束不受影響。建議另案處理。
  • 新的時間斷言（小於 grace 的一半）假設在 macOS 微秒級空窗內沒有其他未加鎖的長壽 spawn 帶走 pipe——與 A1 同一類，累計 50 次以上未觀察到。

對既有 Phase 4 blocker 的影響（待裁決）

計畫與 ADR 0008 記載的 blocker「Host pipe／PTY input/release 沒有 timeout」：release 那一半現在有上限（單一 terminal_release 是既有的終止時限（connector 用 kill_tree，native client 用 terminate_native_client）加上 reader 1 秒，依常數推算 connector 最壞約 7.3 秒、native client 約 3.2 秒，Windows 另含 Job 與 taskkill 的時限；release_all_connectors 約 1.5 秒；不再阻塞等 writer 鎖，先終止再有限等待；以程式結構保證，實際測試只在 macOS 執行過：Unix connector 的 release_does_not_wait_behind_a_blocked_control_write，以及只限 macOS 的 native client 測試 release_does_not_wait_behind_a_blocked_input_write；Linux 要等 PR 的 CI；Windows 的 release 與卡住的寫入沒有在 Windows 上執行過）；Companion 的 10 秒卡住觀測會關閉 stream，經 Lease 走到 Host release：cleanup slot 與 resource／full permit 在 release 返回時歸還，但 write slot 與 device permit 要等卡住的寫入本身返回才歸還。input write 本身仍沒有 timeout：connector 的寫入要等 release 終止子行程、stdin 的讀端全部關閉才會出錯結束；native client 的 PTY 寫入要等 slave 端關閉或被撤銷（macOS 在 session leader 結束時會撤銷 PTY，依據是 lane J 的 pty 實驗，沒有專門的測試）。若另有行程持有 connector stdin 的讀端，寫入在 release 之後仍會卡住，Companion 的 write slot 與 permit 也就不會歸還。持有讀端的可能是忽略 SIGTERM 的同組成員，見上方「殘餘與範圍外」中既有的 kill_tree 行為；也可能是未加鎖的第三方 spawn 帶走的複本。native client 方面，後代若在別的 process group 或 session 裡仍持有 PTY slave，Linux 上卡住的寫入可能不會結束，未驗證。另外，目前沒有「gateway＋真實 HerdrManager＋永不讀取的行程」的端對端測試；永遠不讀、又忽略 SIGTERM 的 leader 在單一 terminal_release 下也沒有測試（kill_tree 升級到 SIGKILL 只由 kill_tree_escalates_to_sigkill_after_grace 另外證明）。文件只加了查證過的註記，blocker 是否解除由使用者決定。
