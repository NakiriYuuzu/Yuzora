問題與修正

資料庫欄位留空時，原實作只嘗試 postgres。若該資料庫不存在或角色沒有 CONNECT 權限，即使其他資料庫可連，也無法開始探索。

  • 留空時依序嘗試 postgres → 與使用者同名的資料庫 → template1，跳過空白與重複候選。
  • 只有 startup SQLSTATE 3D000 與 42501 會換下一個候選；認證、TLS、網路錯誤立即停止。明確指定的資料庫不做備援。
  • 先依原始 profile 驗證 transport 授權，再附加密碼；未放寬明確資料庫綁定的 insecure exception。
  • 所有候選共用原本 15 秒 connection deadline。失敗時保留最後一個 structured code／retryability，並提供各次嘗試的去密診斷；候選用盡時提示指定可連資料庫或申請 CONNECT。
  • 只修改 Rust backend、測試與 fixture；未修改 React src/。

實際驗證

  • Rust 1.96.0；原實作執行最初四個新 regression tests：三個失敗、一個通過。失敗證據為只嘗試 postgres，未進入預期備援。
  • 最終 cargo test --manifest-path src-tauri/host/Cargo.toml --locked db_service::tests --lib：77 通過、0 失敗。共新增六個測試，涵蓋順序、去重、去密錯誤、停止條件、混合失敗與共用 timeout。
  • 最終全 host unit suite：372 通過、22 失敗、1 忽略。22 個失敗名稱與基準完全相同：21 個受此環境的 Unix socket EPERM 限制，1 個為暫存目錄 Git ancestor 假設。不可視為全測試通過。
  • 最終 host integration suites（git_read_efficiency、git_stdio、remote_facade、sqlite_stdio、stdio）：12 通過、0 失敗。
  • cargo clippy --manifest-path src-tauri/host/Cargo.toml --locked --all-targets：通過、零 warning；line-sensitive baseline 沒有 db_service fingerprint，未修改 baseline。
  • Host cargo fmt check、database_integration.rs rustfmt check 與 git diff --check：通過。

剩餘驗證與限制

Loopback protocol fixture 透過真實 tokio-postgres driver 驗證 startup 行為，但不替代真實 PostgreSQL session 驗證。已在既有 Docker integration suite 加入非 superuser 的探索測試：撤銷 PUBLIC 對 postgres 的 CONNECT、同名資料庫不存在、備援 template1 後列出可存取資料庫，並確認 postgres 不在清單。

本環境沒有 Docker／PostgreSQL，也缺少完整 Tauri 所需 GTK／WebKit 系統套件。因此真實 PostgreSQL 與桌面整合驗證待 exact-commit CI；尚未 merge 或 deploy。
