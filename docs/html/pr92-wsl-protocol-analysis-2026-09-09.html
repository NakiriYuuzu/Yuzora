已確認的問題

問題證據與影響
相容性 gate 阻擋host 從 HERDR status --json 讀取 server.compatible；明確為 false 時產生本次錯誤，停用 snapshot、terminal observe／control／create 等能力。這是執行中的 Session 相容性診斷，不是單憑錯誤就能認定安裝包缺少 runtime。
「已載入快照」誤報選定某個 Session 時，工具列直接顯示此文字，未檢查 snapshot 是否存在、connectionState 是否 ready 或是否有錯誤。隔離元件測試在 snapshot=null、unsupported 狀態重現。
空資料與錯誤混在一起沒有 tree roots 就顯示「此 Session 尚無 Space」，未區分查詢失敗與成功查到空集合。這個提示不能證明使用者沒有 Spaces，更不能證明資料遺失。
診斷資訊不足錯誤未帶 client／server version、protocol 或實際 binary；列表又直接印出內部 runtime key。該 key 編碼 WSL registry GUID、預設 UID 與 named Session，並非另一個獨立故障。

已確認的原因與界線

目前 Yuzora 隨附版本固定為 HERDR 0.8.2／protocol 20，使用者保存的 binary 路徑也指向此 managed 版本；其 default socket 上已有 0.9.0／protocol 22 server。0.8.2 status 明確判定 compatible=false，Yuzora 因而阻擋快照與 terminal 操作。此 gate 應保留。

自動啟動流程刻意保留既有 server，不擅自停止與重啟。這解釋了為何重新安裝同一候選不會使兩端版本自動一致。restart_needed 是目前 client 的診斷欄位，不代表應立即用 0.8.2 停止或重啟較新的 0.9.0 server。

尚未驗證 Yuzora 的 API／schema／terminal connector 能否完整支援 protocol 22，因此「更換 binary」或僅修改 protocol 數字不能視為已修復。installer hash 與完整候選實機驗收仍待補齊。

實際執行的驗證

建議處理

  1. WSL 名稱、UID、所選 binary 與 status／session list 已取得並完成比對；另補實際 installer hash。修復優先評估對齊 0.9.0／protocol 22，驗證版本資源、schema、snapshot、events 與 terminal connector，保留現有 server 工作。
  2. 前端分開顯示載入中、unsupported／error、成功但空集合、成功且有資料；快照存在也應區分過期資料。用主機標籤與 Session 名稱取代 raw key。
  3. 利用既有 capability 中的版本與 protocol 欄位，提供可查證的相容性診斷與恢復說明。維持 backend 相容性 gate，不用放寬判斷掩蓋錯誤。
  4. 若需要停止或更換既有 server，先保全使用者工作並確認受影響 Session。修正後重建候選，以同一 Windows／WSL 環境重新驗收；目前 CI 綠燈只代表乾淨 runner 的建置與測試通過。
