測到的行為邊界

前端 suite 涵蓋 application wheel、pointer cell、host history 存在時仍向 HERDR 傳遞 wheel、背壓、不支援指令的 fallback、observe 保護、初次開啟失敗後重試、遠端 stream 中断、重試額度耗盡與手動 Reconnect。這些是元件／transport 測試，不代表遠端 SSH 壓力實測。

Rust suite 包含 stream opening burst 的排隊與 host disconnect 取消。Runtime contract 實際驗證 schema、snapshot、events、observer/controller、輸入、resize、workspace 排序與 scrollback。Native E2E 使用隔離臨時 XDG 與獨立 Session，驗證官方 client、Copy mode/OSC52、Kitty payload、plugin popup/pane、關閉 client 保留 server/pane、普通 connector 重連與同 Session 重開；僅清理測試建立的 runtime。

使用者補充的精確錯誤：host-stream-open-limit

使用者實際訊息為 failed to open herdr terminal: host-stream-open-limit。已核對 HEAD 舊實作：host_stream_open 以 connection.stream_openings.try_acquire() 取得名額，失敗直接回傳该字串；此 semaphore 每 host 有 8 個名額，限制的是同時開啟中的 stream 請求。

工作樹現行 src-tauri/src/host_streams.rs:170 改呼叫 acquire_stream_opening().await。src-tauri/src/host_service.rs:329 提供最多 30 秒排隊並於 host 斷線時取消，逾時字串為 host-stream-open-wait-timeout。這與每 host 已開啟 stream 總數上限、sshd 的 channel 限制是不同層次，該舊錯誤本身不能證明後兩者觸頂。

本次二進位核對：/Applications/Yuzora.app/Contents/MacOS/yuzora 含 host-stream-open-limit；目前 src-tauri/target/debug/yuzora 含 host-stream-open-wait-timeout。兩個版本的程序同時存在。此證據支持優先核對報錯視窗的 App build，尚不能從訊息 alone 判定使用者當時的 PID。

重新執行 cargo test --locked --lib host_service::tests::stream_openings_queue_behind_a_burst_and_cancel_with_the_host -- --exact：1 passed。測試占滿 8 個名額，確認第 9 個等待、釋放後成功，以及 host 斷線時取消。另直接以現行 isRetryableHerdrConnectError(new Error("host-stream-open-limit")) 核對，得到 temporary / retryable=true。未以使用者 SSH 主機重現 burst，故不宣稱遠端實機問題已驗收通過。

此錯誤發生於 Rust HostConnection 層；更換 Chromium 引擎不會直接改變該 semaphore／connector 開啟流程。也不應把修復它等同於把 HERDR client 從 0.9.1 換成 0.9.3。
