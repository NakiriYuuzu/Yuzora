記憶體與資源洩漏掃描

確認 4 類回收缺口，另發現 1 項 PostgreSQL 記憶體成長風險。最優先是遠端 HERDR 的 Channel callback：重複建立與關閉後，callback 數量持續上升。

這次檢查涵蓋前端、Tauri Rust、host helper、官網與 Remotion 原始碼的資源生命週期模式，並追查高風險路徑。新增的檔案只有本報告與驗證資料；產品程式碼未修改。

「確認」指實際專案模組在模擬 I/O 下可重現保留引用或漏掉釋放。沒有執行瀏覽器自動化、原生 heap／RSS 壓測或真實 PostgreSQL 大結果測試，因此不把測試計數換算為整個 App 的實際記憶體用量，也不宣稱已排除所有平台及第三方套件的洩漏。

已確認的回收缺口

P1M1：遠端 HERDR 多建立一層無人回收的 Channel

herdrTerminalOpen 與 herdrEventsSubscribe 先建立 Tauri Channel。遠端路由進入 openStream 後，又建立一個 Channel 交給 host_stream_open；原本的 Channel 僅透過 output.onmessage(...) 在 JavaScript 內轉送事件。

已安裝的 Tauri API 在 Channel 建構時呼叫 transformCallback，由全域 callback 表強引用該物件，收到 Rust 的 end 訊息才 unregisterCallback。第一層 Channel 沒有送到 Rust，無法收到這個訊號；程式亦未釋放它。GC 因此不能自動回收該 callback 與其可達閉包。終端機路徑的閉包會連到事件處理與 terminal effect 環境。

terminal 開啟／釋放 100 次 → callbacks = 100
再做 events 訂閱／釋放 100 次 → callbacks = 200
nativeStreams = 0

驗證使用實際 Channel 與實際 HERDR wrapper/provider；模擬 Rust 正確回傳 end，確保遺留的不是測試未關閉的 native Channel。正常結束的遠端串流也會觸發，並非只發生於錯誤路徑。

建議：將 Channel 的建立集中於實際跨 IPC 的邊界；provider 之間以一般事件函式傳遞，使每個原生 Channel 都有明確 owner，並涵蓋成功、開啟失敗、斷線與取消。

來源：src/lib/herdrIpc.ts:248、352；src/lib/herdrProvider.ts:100–130；@tauri-apps/api/core.js:73–123。

P2M2：關閉分割區及讀取競態會留下完整文件

路徑 A：關閉右側編輯區。EditorArea 的按鈕直接呼叫 closeSplit。該動作移除右側 tabs，但沒有執行一般分頁關閉流程中的 dropDocument。EditorPane 卸載會 updateBuffer、unregister view 及 destroy CodeMirror，文件字串仍由全域 registry 持有。

重複：splitRight → openTabInGroup → getDocument → closeSplit
25 次後：openTabs = 0
重新探查 25 個已關閉的 path：新增檔案讀取 = 0，全部命中舊快取

路徑 B：在檔案讀取完成前關閉分頁。getDocument 只檢查 workspace epoch 與 path identity；dropDocument 只刪當下快取，沒有使 in-flight read 失效。讀取稍後完成，仍會 registry.set。EditorPane 的 disposed flag 可以阻止建立畫面，卻不能阻止 registry 插入內容。局部測試重現 drop → late resolve → get 命中同一份快取。

兩條路徑保留的是內容，不只是小型 path 記錄；檔案越大，影響越明顯。切換工作區時 clearAll 會釋放文件內容，因此屬於工作區生命週期內可累積的保留。

建議：以仍然開啟的文件 owner 統一清理 registry；最後一個 owner 關閉時同步使該文件的讀取 token 失效。分割區關閉需要接入正常的儲存／捨棄與文件釋放流程。

來源：src/state/workspaceStore.ts:1132–1143；src/workbench/EditorArea.tsx:79；src/editor/EditorPane.tsx:148–158；src/editor/documentRegistry.ts:17–35。

P2M3：遠端斷線的清理被 stale guard 提前阻擋

unregisterRuntimeHost 只移除 hosts。之後 native 串流送來 closed 時，事件處理在檢查 hosts identity 失敗後直接 return，沒有刪掉 streams entry。呼叫 herdrEventsRelease／herdrTerminalRelease 又會先執行 ensureCurrent(stream.host)，因此在 streams.delete 前拋出 StaleRuntimeResponse。

斷線、重連與再次開啟會留下不同 generation 的 entries，各自強引用舊 RuntimeHost、owner 與 session inventory。Rust 的 disconnect 本身會清理原生 streams/tunnels；本項發現位於前端登錄表。

25 個 generation：open → unregister host → native closed/end → release
25 個舊 ID 的 release 都拋 StaleRuntimeResponse
對應 release 沒有執行 native close；如果 entry 已刪除，本來應直接成功返回

建議：斷線時先清除該 owner 的前端登錄；closed 事件的 bookkeeping 應能處理過期 owner。release 在 host 過期時也必須能完成本地移除，輸入與其他操作仍保留 identity gate。

來源：src/lib/herdrProvider.ts:45–47、107–114、163–173；src/state/hostStore.ts:close；src-tauri/src/host_service.rs:465–482。

P2M4：舊遠端工作區持續占用 capability 與目錄 handle

registerRuntimeWorkspace 會向 host 開啟 capability，並把它記在模組層的 workspaces Map。一般 workspace 切換只清文件快取與更新 workspace store，沒有釋放舊 capability。現有 workspaceClose 主要處理開啟失效與重複 canonical 路徑，沒有正常退場的引用計數／淘汰路徑。

host 的 WorkspaceFiles 為每個 capability 保留 PinnedDir，並在 128 個 entries 時拒絕新的 open。不同路徑持續加入會消耗這個有限資源；即使前端現在只使用一個 workspace，舊紀錄仍在。runtime folder／SQLite 瀏覽器也會走此註冊邊界。

實際前端註冊與 workspace store，模擬 host 的真實上限規則：
不同路徑註冊 128 次 → retained capabilities = 128，workspaceClose = 0
第 129 個 → too-many-workspaces

這是有上限的資源保留問題；測試中的 host registry 是模擬值，128 上限與 PinnedDir ownership 另由 Rust 原始碼確認。未聲稱量測了真實的 128 個 OS handle。

建議：以文件／瀏覽器／工作區消費者持有的 lease 管理 capability；最後使用者離開時 workspaceClose，並移除無人使用的 revisions/backend closure。最近使用清單只需保存可重開的識別資料。

來源：src/lib/remoteFiles.ts:14–16、138–159；src/lib/workspaceActions.ts:62–64；src-tauri/host/src/files.rs:59–74。

高風險記憶體成長路徑

P1 風險R1：PostgreSQL helper 將資料流轉成無界 Row 佇列

helper_pg_query 建立 mpsc::unbounded_channel，獨立 reader task 不斷 try_next 並同步 send 每列。consumer 需轉換欄位並寫 stdout；當桌面端取得第一頁後等待使用者翻頁，stdio 的 backpressure 只會擋住 consumer，reader 仍可把資料庫輸出搬進記憶體佇列。

raw row 的大小檢查也在出佇列之後，這部分記憶體不在桌面 ResultSessionRegistry 的 64 MiB/session、256 MiB/process 預算中。大結果或慢速消費可能使 helper 記憶體上升，直到查詢讀完、取消，或被記憶體保護停止。

現有保護：helper 約 512 MiB 上限；Unix 為 RSS watchdog（有採樣間隔，部分平台另有 address-space fail-safe），Windows 為 Job Object process memory limit。這可限制故障範圍，無法取代預讀 backpressure。此項屬於可從 source 確認的無界緩衝設計，尚未量測真實 PostgreSQL 下的成長曲線，不能等同永久不可回收洩漏。

建議：改為小容量、有 await backpressure 的 row channel，讓取消能打斷 blocked send；必要時加 byte budget。驗收使用大結果查詢，停在第一頁並觀察 helper RSS 是否穩定，再確認取消與關閉能回收。

來源：src-tauri/host/src/db_service.rs:3003–3011、3082、3115、5839；src-tauri/host/src/db_query_worker.rs:44–45、236–306。

其他值得限制的長期保留

以下未列入上面的四類已重現缺口，避免將刻意快取、條件式風險與實際洩漏混為一談。

  • documentRegistry.ts:74–78 的 generations 明確跨 clearAll 保留；不同路徑逐步累積。可考慮 workspace epoch／開啟 token，避免永久保存歷史路徑。
  • herdrStore.ts:219–224、372–396 保留 runtimesBySession；session 清單更新沒有同步移除消失的 runtime。需在永久刪除與暫時斷線之間定義淘汰政策。
  • gitLogStore.ts:76、93、281 的 author cache 刻意在 repo 切換時保留，缺少容量上限；commit detail cache 則已有 50 筆限制。可替 author cache 加 LRU。
  • updateStore.ts:46–55、145–151 替換／reset Update 時沒有呼叫 Update.close()；Tauri Resource 不由 JS GC 回收，下載 bytes 也由 Rust resource table 持有。但目前 UI 在 available/downloaded 狀態不提供重複 check，reset 主要是測試入口，因此僅列成生命週期防護缺口，未宣稱一般點擊操作可持續重現。

掃描與驗證範圍

資源模式掃描涵蓋 src/、src-tauri/src/、src-tauri/host/src/、site/、site-remotion/src/ 共 327 個非獨立測試 TS／TSX／JS／Rust 檔案候選；Rust inline tests 仍在檔案內。這是全範圍模式掃描加生命週期追查，不代表逐行驗證了每一個分支。

區域檢查內容與結果
React／編輯器／UI事件、interval、timeout、observer、RAF、CodeMirror view、Blob URL、stores／Map。檢查到的 observer/listener 多有對應清理；SVG Object URL 有 revoke。文件 registry 缺口見 M2。
Terminal／HERDRoutput queue 有界、輸入有 256 KiB cap、unmount dispose 與晚到 open release；遠端 wrapper callback 與斷線 Map 缺口見 M1/M3。
Host／SSH／SFTP／tunnelstream queue、連線 generation、disconnect、Drop、helper 子程序、transfer 取消、JoinSet abort/drain。既有 streams/tunnels 有上限；workspace capability 缺口見 M4。
資料庫actor settlement、result cache、connection release、worker process containment。結果快取預算相關 15 個測試通過；PostgreSQL 原始 row queue 風險見 R1。
Browser／Git／搜尋／log／perfnative WebView close、遠端 tunnel lease、watcher join、取消與快取上限。原生 WebView 的 allocator／平台程序未做 heap 驗證；不據此宣稱完全無洩漏。
官網／Remotion／vendor官網與影片程式納入事件／計時器模式掃描；靜態頁面的整頁生命周期 listener 不直接當成洩漏。vendored Tiberius 補查 raw ownership/leak 模式，未進行第三方 driver 全面動態稽核。

codebase-memory 索引已更新，引用的主要檔案均確認 metadata_match。索引有兩份 CSS 的局部解析缺口；i18n、測試、vendor、文件、build output 等為設計上排除，已按用途做直接來源補查。node_modules 僅核對 Tauri Channel／Resource 的實際套件實作；外部 HERDR binary、OS WebView 與所有第三方依賴不在完整動態驗證範圍。
