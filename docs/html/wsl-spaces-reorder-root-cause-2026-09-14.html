WSL Spaces 排序：舊 helper 被新 App 繼續使用

2026-09-14 · Windows App 原生畫面、Ubuntu-26.04 唯讀 runtime 探測、同一資料回放。分析基準 release/v0.0.14，03d6778058d274f9bc719d4a6040df09ce69e549。

已證實根因：桌面 App 已更新到 v0.0.14，但 WSL 仍執行 v0.0.13 的 yuzora-host。舊 helper 不認識新排序能力欄位；前端將缺失值判為不可用，因而同時停用拖曳及上移／下移。HERDR client、server 均為 0.9.0／protocol 22，並非 HERDR 版本過舊或 WSL 不支援排序。

實機證據與控制變因

Windows 主機 DESKTOP-NMLUN4F（RDP 192.168.213.129）；App 設定顯示 v0.0.14。Ubuntu-26.04 的已保存 helper 路徑與 /proc/*/exe 實際執行路徑一致，皆屬於 v0.0.13 目錄。兩輪獨立唯讀探測均回傳 helper 0.0.13、缺失 workspaceMove／workspaceMoveBlock。

對照只更換診斷子行程的 helper：舊 saved helper 與 C:\Program Files\Yuzora\host\linux-x86_64\yuzora-host。兩者使用相同的舊目錄 HERDR binary、同一 default Session／socket。新 helper 直接從現有安裝包讀取；沒有更換使用者設定或停止 HERDR server。

實際 herdr api schema --json 包含 workspace.move 與 workspace.move_block。舊 helper 的 API methods 卻只回報 workspace.close／create／focus／rename；新 helper 追加 move／move_block 並回傳兩個 true。舊欄位是不存在，不是 HERDR 明確回報 false。

故障鏈與程式位置

  1. src/state/hostStore.ts:18 讀取持久化 binary／helper 完整路徑；selectionForHost 只辨識來源政策，沒有換成新 artifact 路徑。
  2. src/state/hostStore.ts:172 已連線時只執行 hello 健康檢查；src/state/hostStore.ts:184 重連仍使用 config.helper，接著使用 config.binary。此路徑未比較當前安裝包的 artifactIdentity 或呼叫 prepareHost。
  3. src-tauri/src/host_service.rs:401 握手檢查 host protocol 與作業系統。兩代 helper 都回報 protocol 1，因此舊 helper 可正常連線；此檢查不代表新 HERDR 子命令與欄位已完整實作。
  4. src-tauri/host/src/herdr_service.rs:244 v0.0.14 新增排序欄位，並由 src-tauri/host/src/herdr_service.rs:3956 schema 判定；v0.0.13 tag 的 helper 不含這些欄位和 workspace move 指令。Windows native 使用目前 App 編譯進去的 facade，WSL 使用獨立保存的 helper，因而出現平台差異。
  5. src/lib/herdrTypes.ts:92 允許排序欄位缺失；src/lib/herdrWorkspaceActions.ts:9 將 undefined 轉成 false。
  6. src/app/workbench/SpaceAgentTree.tsx:204 pointerdown 在建立 gesture 前直接 return；src/app/workbench/contextMenuDefs.ts:253 同時回傳 herdrMethodUnavailable。這解釋為何修 pointer capture 無法解除本次問題。
  7. src/app/workbench/HerdrSettingsSection.tsx:152 必須先進設定執行檢查，才取得 desired artifact；src/app/workbench/HerdrSettingsSection.tsx:186 才顯示工具可更新。安裝新版 App 本身沒有完成這一步。

已排除與尚未驗證

檢查結果依據
HERDR client／server 不相容已排除皆 0.9.0、protocol 22、compatible=true、restart_needed=false。
HERDR schema 缺少排序已排除同一 binary 的實際 schema 與新 helper 能力皆存在。
兩個 root 的 worktree metadata 不完整已排除w8／w9 inventories 均成功；實際資料通過 herdrReorderMembers 與 expectedOrder 驗證。
當前 UI 拖曳／選單排序FAIL原生已見停用，順序維持 Yuzora → couple-expense；實機回放產生同一 disabled reason。
新 helper 配原資料的前端排序條件PASS相同真實 snapshot／inventory，僅更換真實 capabilities 回應。
套用 helper 更新後的原生拖曳、API mutation 與 Session 延續NOT RUN本次為診斷，未套用設定或發送排序 mutation；回放 PASS 不等於原生修復驗收。

現有前端排序 11 tests、Rust workspace.move／move_block schema gate 與 protocol 22 fixture 測試皆通過；它們沒有覆蓋「新 App 搭配仍保存的舊 helper」。現有前端 fixture 直接將排序 flags 設為 true，無法捕捉此升級缺口。

對應修復方向

  1. 更新此 WSL 主機的 Yuzora helper，保持 HERDR 來源政策，部署到新的不可變 artifact 目錄；重驗既有 Session 相容後才切換。不必升降 HERDR 或停止原 server。
  2. App 升級／重連時比較實際 helper artifact identity，對過期 helper 提供更新或相容路由；不能因 host protocol 1 相同就假設新命令存在。HERDR binary 與 helper 應分別驗證。
  3. 區分「helper 未實作」「HERDR 不支援」「未知」「不相容」，讓選單指出真正原因；不能只強制 capability 為 true，舊 helper 同樣缺少 mutation 指令。
  4. 加入跨版本 helper 契約與既有 host config 升級回歸。切換後對所有受影響 Session 重新取得 capabilities，驗證原生上下移／拖曳、權威 workspace order，以及原 Session／pane／process 存續。
